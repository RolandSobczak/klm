# 15 — Project Scaffolding and CI/CD

Turns a KiCad project into a repository that proves it is self-contained and publishes its own
artifacts. Two capabilities:

- **`klm scaffold`** — generate the repository furniture (workflows, ignore rules, config, README).
- **Clean-room verification** — the check that makes "a collaborator can open this" a fact rather
  than a hope.

## 1. Why CI is the only honest self-containment test

`klm vendor` ([06](06-library-sync.md)) copies parts into the project and rewrites references.
Verifying it worked **on your own machine is close to meaningless**: your `KLM` global library is
registered, `KLM_LIBS` is set, and your 3D models are on disk. A project that still references
`KLM:STM32F103C8T6` in one forgotten sheet opens perfectly for you and shows a broken-symbol
placeholder for everyone else.

A CI runner is a clean machine. No global libraries, no environment variables, no catalog. If the
project resolves there, it resolves for a collaborator. That is the whole argument, and it's why
this feature belongs to the sync story rather than being a separate nicety. See
[ADR-0007](adr/0007-clean-room-verification.md).

**Consequence for the implementation:** `klm verify --clean-room` must work with **no catalog and
no configuration**, using only files inside the repository. It's a different code path from
`klm lint`, which assumes the catalog exists.

## 2. `klm scaffold`

```bash
klm scaffold                      # interactive; asks what to include
klm scaffold --preset publish     # verify + artifacts + release
klm scaffold --preset private     # verify only
klm scaffold --check              # report drift from the current klm's templates
klm scaffold --update             # regenerate, preserving marked user edits
```

Generated files:

```
.github/
  workflows/
    verify.yml            PR + push: clean-room check, ERC, DRC, lint
    artifacts.yml         merge to main: PDFs, BOM, fab package
    release.yml           on tag: the above, attached to a GitHub Release
  pull_request_template.md
.gitignore                KiCad-aware
.gitattributes            line endings, LFS, binary markers
.pre-commit-config.yaml
klm.toml                  project config: variants, fab profile, verification policy
README.md                 board README template
```

Every generated file carries a header so `--check` can detect drift and `--update` can regenerate
without clobbering deliberate edits:

```yaml
# Generated by klm scaffold 0.6.0 — edits below the marker are preserved.
# Regenerate: klm scaffold --update
# --- klm:managed ---
...
# --- klm:end ---
```

### `.gitignore`

KiCad produces a lot of noise that must not be committed:

```gitignore
# KiCad backups and autosaves
*-backups/
*.kicad_prl
*.kicad_sch-bak
*.kicad_pcb-bak
_autosave-*
*.000
*.bak

# Caches — machine-specific, cause spurious diffs
fp-info-cache
*.lck

# Build output
/fab/
/artifacts/
```

Two entries deserve comment. `*.kicad_prl` holds per-user local project settings (open sheets,
active layer) and generates a diff on every session. `fp-info-cache` is a machine-local footprint
index; committing it produces conflicts that mean nothing.

### `.gitattributes`

```gitattributes
* text=auto eol=lf
*.kicad_sch  text eol=lf
*.kicad_pcb  text eol=lf
*.kicad_sym  text eol=lf
*.kicad_mod  text eol=lf
*.step       text eol=lf   # ASCII, but large — see LFS note below
*.pdf        binary
*.png        binary
```

CRLF in a `.kicad_pcb` produces a whole-file diff and can confuse tooling; forcing LF is the
single highest-value line here. If the project vendors 3D models, scaffold optionally adds
`*.step filter=lfs diff=lfs merge=lfs -text` — though the default for a collaboration repo is
`klm vendor` without 3D models at all ([04 §4](04-catalog-and-storage.md#3d-models-and-git)).

## 3. Clean-room verification

`klm verify --clean-room` is the gate. It runs against a fresh checkout with nothing installed
and no catalog.

| Check | Severity | Why it matters |
|---|---|---|
| Every `lib_id` in the schematic resolves within the repo | error | The core self-containment guarantee |
| No `lib_id` references a known-global prefix (`KLM:`) | error | Catches partial vendoring |
| Project `sym-lib-table` / `fp-lib-table` exist and use `${KIPRJMOD}` | error | Absolute or `${KLM_LIBS}` paths break on any other machine |
| Every footprint referenced by the PCB exists in the repo | error | |
| Every `(model …)` path resolves, or the model is deliberately absent | error / info | Absent 3D is fine and expected; a *broken* path is not |
| No absolute filesystem path anywhere in any project file | error | `/home/rsobczak/...` is the classic leak |
| A path is a path, not a net name | — | see below |
| No reference to an undeclared environment variable | error | `${MY_LIBS}` a collaborator doesn't have |
| `klm.lock.json` matches the vendored library contents | error | Catches a hand-edited library that diverged |
| ERC clean | error | |
| DRC clean | error | |
| Every part has the fields the project's policy requires | warning | Configurable in `klm.toml` |

The last five are the difference between "it opens" and "it's actually usable" — a project that
renders correctly but fails DRC isn't ready to hand to anyone either.

**The absolute-path check has to be conservative.** KiCad quotes net names (`/SDA`, `/BAT+`) and
hierarchical sheet paths (`/3a1f-…/c4d2-…`) exactly like POSIX paths. Flagging every quoted string
that starts with a slash produced **124 false errors against 2 true ones** on one real board, which
is a check people learn to ignore. klm requires a directory component *and* a filename with an
extension, or an unambiguous Windows/UNC prefix. The precise cases — `(model …)` references and
library-table URIs — are checked by name elsewhere; this is only the backstop for a leak somewhere
nobody thought to look.

ERC and DRC are not run by `klm verify`: they are `klm fab --check`'s job, and the scaffolded
workflow runs both. Splitting them keeps verification free of `kicad-cli`, so the same command works
in a pre-commit hook on a machine that has no KiCad.

```
$ klm verify --clean-room
✓ symbol resolution        47 symbols → libraries/my-board.kicad_sym
✓ footprint resolution     47 footprints → libraries/my-board.pretty
✓ library tables           project-level, ${KIPRJMOD}-relative
✓ no global references
✓ no absolute paths
ℹ 3D models                omitted (vendored with --no-3d)
✓ lock file                consistent, 47 parts
✓ ERC                      0 errors, 0 warnings
✗ DRC                      2 errors
    my-board.kicad_pcb  clearance violation  F.Cu  (128.5, 94.2)
    my-board.kicad_pcb  unconnected item     net /SDA

FAILED — 1 check
```

Exit non-zero on any error. `--format json` for machine consumption; `--format github` emits
[workflow commands](https://docs.github.com/actions) so findings appear as annotations on the
right file and line in the PR diff.

## 4. The verify workflow

```yaml
name: verify
on:
  pull_request:
  push:
    branches: [main]

jobs:
  verify:
    runs-on: ubuntu-latest
    container:
      image: kicad/kicad:9.0.9-full   # pin exactly — see §7
      options: --user root            # see the note below
    steps:
      - uses: actions/checkout@v4
        with:
          lfs: true

      - name: Install klm
        run: pipx install klm==0.6.0   # pinned; see §7

      - name: Clean-room verification
        run: klm verify --clean-room --format github

      - name: Lint
        run: klm lint --project . --max-severity warning --format github
```

Note what is *absent*: no secrets, no catalog, no `klm init`. That's deliberate — the workflow
must run on a pull request from a fork, where secrets are unavailable by design. Anything needing
credentials (live stock checks) goes in a separate, optional workflow that runs only on branches
in the main repository.

**`options: --user root` is not optional.** The official KiCad image ends with `USER kicad`, while
a container job's workspace is created by the runner as root — so `actions/checkout` fails on
permissions before anything else runs. This was found by reading
[the Dockerfile](https://github.com/KiCad/kicad-docker) rather than by a first broken CI run, and
without it every scaffolded repository would fail on its first push ([Q11](14-open-questions.md#q11)).

**The `-full` image is the right one**, and it settles a question
[ADR-0010](adr/0010-vendoring-leaves-unmanaged-libraries-linked.md) deferred to this phase. Clean-
room verification asks "does this resolve on a machine that has nothing?" — but KiCad's standard
libraries ship *with KiCad*, so any machine that can open the project has them. The honest
definition is: no klm catalog, no klm global libraries, no user configuration, but a stock KiCad.
`-full` provides exactly that, which lets `klm verify` answer the `power:GND` versus
`Passive:0R_0603` question by *trying to resolve them* — no list to maintain, no dependence on the
author's machine.

## 5. The artifacts workflow

Runs on merge to `main`, and on tags for releases.

| Artifact | Produced by | Purpose |
|---|---|---|
| `schematic.pdf` | `kicad-cli sch export pdf` | The thing people actually want to look at |
| `board-top.png` / `board-bottom.png` | `kicad-cli pcb render` | Visual review without opening KiCad |
| `board.step` | `kicad-cli pcb export step` | Mechanical/enclosure work |
| `bom.csv` | `klm bom` | Machine-readable |
| `bom.html` | `klm bom --format html` | Grouped, with prices and stock at generation time |
| `fab-<variant>.zip` | `klm fab` | Gerbers, drill, CPL, assembly BOM — ready to upload |
| `ibom.html` | interactive BOM tool (optional) | Interactive placement aid for hand assembly |

```yaml
name: artifacts
on:
  push:
    branches: [main]
  workflow_dispatch:

jobs:
  build:
    runs-on: ubuntu-latest
    container: kicad/kicad:9.0
    strategy:
      matrix:
        variant: [basic, full]
    steps:
      - uses: actions/checkout@v4
      - run: pipx install klm==0.6.0

      - name: Preflight
        run: klm fab --check --variant ${{ matrix.variant }}

      - name: Build fabrication package
        run: klm fab --variant ${{ matrix.variant }} --out artifacts/

      - name: Documentation
        run: klm docs --pdf --render --bom --out artifacts/

      - uses: actions/upload-artifact@v4
        with:
          name: my-board-${{ matrix.variant }}
          path: artifacts/

      - name: Job summary
        run: klm report --format github-summary >> $GITHUB_STEP_SUMMARY
```

The matrix over variants is what makes this worth automating — building `basic` and `full`
packages by hand every time a revision lands is exactly the tedium that stops happening.

`klm report --format github-summary` writes a Markdown table into the Actions run summary: board
revision, part count, estimated BOM cost at qty 5/10/25, DRC/ERC status, and a link to each
artifact. That summary is visible without downloading anything, which is most of the value.

### Releases

On a tag, the same artifacts attach to a GitHub Release, so `v1.2.0` is a permanent, downloadable
snapshot of the fab package that produced a physical board. Given that boards get ordered from
a specific commit and arrive weeks later, a durable tag→artifact link is genuinely useful for
answering "which files did I actually send?"

## 6. Optional: PR visual diff

A workflow that renders the board before and after and posts both images plus a schematic diff as
a PR comment. Reviewing a PCB change from a unified diff of S-expressions is not realistic;
reviewing it from two images is.

This is listed as optional because it needs a bot token to comment and doubles CI time. It's the
single most-appreciated feature in PCB repositories that have it.

## 7. Reproducibility concerns

Three things will bite, and all three are avoidable.

**Pin every version.** An unpinned `kicad/kicad:latest` means the same commit produces different
gerbers next month. Pin the container tag and the klm version; scaffold writes them explicitly and
`klm scaffold --check` warns when they drift far behind.

**Gerbers contain timestamps, and KiCad offers no way out.** Two runs of the same commit produce
byte-different files, so artifacts cannot be diffed across runs. KiCad does **not** honour
`SOURCE_DATE_EPOCH` — `GbrMakeCreationDateAttributeString` reads the wall clock unconditionally,
with no environment override of any kind ([Q11](14-open-questions.md#q11)). So
`klm fab --normalize-timestamps` post-processes the emitted files. Off by default, on in CI.

It **replaces** the timestamp rather than zeroing it, which is a change from what this document
originally said. A well-formed `%TF.CreationDate,1980-01-01T00:00:00+00:00*%` cannot upset a parser
that accepted the original, whereas a blanked field plausibly could — so substituting a fixed valid
value closes the parser risk by construction instead of by testing against an upload. Normalisation
runs *before* the gerbers are zipped, or the archive would preserve exactly what it came to remove.

**Headless rendering — still unverified, and honestly so.** Some `kicad-cli` operations have
historically needed an X server even for non-interactive export; `pcb render` is the usual suspect.
The scaffolded workflow wraps render steps in `xvfb-run`, which costs nothing if unnecessary. This
is the one part of [Q11](14-open-questions.md#q11) that a first real CI run has to answer, along
with the exact `kicad-cli` flag surface — KiCad is not installed on the development machine, so
`klm docs` and the export wrappers are tested against an injected runner rather than the tool.

`klm docs` therefore treats each artifact independently: one that cannot be produced is *reported*
and the others still are. Losing the schematic PDF because the 3D render wanted a display would be
a poor trade.

## 8. `klm.toml`

The project-level config the workflows read, so CI behaviour is version-controlled data rather
than YAML scattered across workflow files:

```toml
[project]
name = "sensor-board"
revision = "rev-c"

[verify]
require_3d_models = false
require_fields = ["MPN", "Manufacturer", "LCSC"]
allow_absolute_paths = false
max_severity = "warning"

[variants.basic]
dnp = ["U5", "J3", "R17"]

[variants.full]
dnp = []

[fab]
profile = "jlcpcb"
normalize_timestamps = true

[artifacts]
schematic_pdf = true
board_render = true
step_export = true
interactive_bom = true
```

Changing what CI does is then a one-line edit to a config file, reviewable in a PR, rather than a
workflow rewrite.

## 9. The README template

Scaffold generates a board README that stays true, because CI fills the moving parts:

```markdown
# sensor-board rev-c

[![verify](https://github.com/USER/REPO/actions/workflows/verify.yml/badge.svg)](…)

STM32-based environmental sensor board. 4-layer, 1.6 mm, ENIG.

## Opening this project

Clone and open `sensor-board.kicad_pro` in KiCad 9. All symbols, footprints and
libraries are contained in this repository — no external library setup is required.

## Downloads

Latest artifacts from the [most recent main build](…):
schematic PDF · BOM · fabrication package.

## Building

| Variant | Description |
|---|---|
| `basic` | Core function, no radio |
| `full`  | All options populated |
```

The "no external library setup is required" claim is the one the verify workflow enforces on every
push. A README that asserts something CI proves is worth more than one that asserts something
nobody checks.

## 10. Commands

```bash
klm scaffold [--project .] [--preset publish|private] [--check] [--update]
klm verify --clean-room [--project .] [--format text|json|github] [--require-3d]
klm docs [--project .] [--all | --pdf --render --step] [--output DIR]
klm report [--project .] [--variant v] [--package DIR] [--format markdown|github-summary|json]
klm fab --normalize-timestamps [--format text|github]
```

## 11. What this deliberately does not do

- **Auto-order from CI.** Spending money from a merge commit is not a feature.
- **Auto-tag or auto-release.** Releases are a human decision.
- **Require klm to open the project.** A collaborator clones and opens it in KiCad. klm exists in
  CI and on your machine; the repository itself has no klm dependency ([06 §6](06-library-sync.md#6-collaboration-workflow)).
- **Support non-GitHub forges initially.** The verification and artifact commands are
  forge-agnostic; only the generated workflow files are GitHub-specific. GitLab CI templates are
  a straightforward later addition since all the real work happens in `klm` subcommands.
